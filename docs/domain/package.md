# Устройство пакета PPTX

## §1. Пакет — это ZIP по стандарту OPC

`.pptx`, `.potx`, `.ppsx` — один и тот же формат контейнера, различаются только
типом содержимого главной части. Для чтения различать их не нужно: код открывает
любой из них одинаково.

Внутри — «части» (parts), адресуемые именами вида `/ppt/slides/slide1.xml`.
В ZIP они лежат без ведущего слэша: `ppt/slides/slide1.xml`. Наш ридер нормализует
имена к виду с ведущим слэшем и сам снимает его при чтении из архива.

## §2. Точка входа

```
/[Content_Types].xml     карта типов содержимого
/_rels/.rels             связи пакета
```

В `/_rels/.rels` ищется связь с типом
`…/officeDocument/2006/relationships/officeDocument` — её цель и есть главная
часть, обычно `/ppt/presentation.xml`. Имя не гарантировано, идти надо по типу
связи, а не по пути.

## §3. Связи

Связи части `/ppt/slides/slide1.xml` лежат в
`/ppt/slides/_rels/slide1.xml.rels` — то есть в подкаталоге `_rels` рядом с
частью, имя файла плюс `.rels`.

Формат:

```xml
<Relationship Id="rId2"
              Type="http://schemas.openxmlformats.org/officeDocument/2006/relationships/slideLayout"
              Target="../slideLayouts/slideLayout2.xml"/>
```

Три правила:

1. `Target` **относителен каталогу части**, а не корню пакета. Разрешать через
   нормализацию `posixpath`.
2. `TargetMode="External"` означает, что цель — не часть пакета, а URL или путь
   на диске. Такие связи не разрешаются в части и хранятся отдельно.
3. `Id` уникален только внутри одной части. Ссылки в XML идут через
   `r:embed`, `r:id`, `r:link` и разрешаются в контексте своей части.

## §4. Граф документа

```
/ppt/presentation.xml
   ├─ sldMasterId → /ppt/slideMasters/slideMasterN.xml
   │                   ├─ theme      → /ppt/theme/themeN.xml
   │                   └─ sldLayoutId → /ppt/slideLayouts/slideLayoutN.xml
   └─ sldId       → /ppt/slides/slideN.xml
                       └─ slideLayout → /ppt/slideLayouts/slideLayoutN.xml
                                           └─ slideMaster → …
```

Ключевые моменты:

- **Порядок слайдов задаёт `p:sldIdLst` в `presentation.xml`**, а не имена файлов.
  `slide7.xml` может быть вторым в колоде. Всегда идти по списку.
- Слайд связан ровно с одним макетом, макет — ровно с одним мастером, мастер —
  ровно с одной темой. Тема достижима из слайда только через эту цепочку.
- Мастеров может быть несколько, и у каждого своя тема. Значит «палитра шаблона»
  — не одна: собирать по мастерам и указывать, какой относится к каким слайдам.

## §5. Что ещё лежит в пакете

| Часть | Зачем нам |
|---|---|
| `/ppt/theme/themeN.xml` | палитра, шрифты, стили заливок — `DOM-COLOR` |
| `/ppt/notesSlides/…` | заметки докладчика, см. `OQ-08` |
| `/ppt/media/…` | изображения и видео; имена ничего не значат, идти по связям |
| `/ppt/embeddings/…` | внедрённые книги Excel за диаграммами |
| `/ppt/fonts/…` | внедрённые шрифты, если автор включил вложение (`OQ-04`) |
| `/docProps/app.xml` | заголовки слайдов, иногда полезно как подсказка |

## §6. Ключевые поля `presentation.xml`

```xml
<p:sldSz cx="12192000" cy="6858000" type="screen16x9"/>
<p:notesSz cx="6858000" cy="9144000"/>
<p:defaultTextStyle>…</p:defaultTextStyle>
```

`p:sldSz` — размер холста в EMU, последний уровень наследования геометрии.
`p:defaultTextStyle` — последний уровень наследования текста (`DOM-TEXT §2`).

## §7. Практические грабли

- Файл может быть собран так, что `[Content_Types].xml` объявляет часть через
  `Default` по расширению, а не через `Override`. Полагаться на `Override` нельзя.
- Некоторые генераторы кладут в ZIP каталоги как отдельные записи с нулевой
  длиной. Пропускать записи, имя которых кончается на `/`.
- Пути в `.rels` встречаются и со слэшами Windows у кривых генераторов.
  Нормализовать разделители до чтения.

## §8. Markup Compatibility: префиксы, на которые ссылаются значения

Пространство имён Markup Compatibility (`mc`) позволяет файлу нести куски
разметки для разных версий Office. Ссылки на пространства имён в нём устроены
**не как везде**: префикс указывается текстом внутри значения атрибута.

```xml
<p:sld xmlns:mv="urn:schemas-microsoft-com:mac:vml" mc:Ignorable="mv"
       mc:PreserveAttributes="mv:*">
```

```xml
<mc:AlternateContent>
  <mc:Choice Requires="v"> … </mc:Choice>
</mc:AlternateContent>
```

Атрибутов с таким поведением пять: `Ignorable`, `PreserveAttributes`,
`PreserveElements`, `ProcessContent`, `Requires`.

**Грабли.** `xml.etree.ElementTree` объявляет при сериализации только те
пространства имён, которые встретились в **именах** элементов и атрибутов.
Префикс, названный лишь внутри значения, объявления не получает. Ссылка
остаётся, объявление исчезает — и файл перестаёт быть валидным по правилам MCE,
оставаясь синтаксически корректным XML.

**Чем это кончается.** PowerPoint отвечает `E_FAIL` и не открывает файл вовсе.
Ни `python-pptx`, ни собственный разбор, ни проверка целостности пакета этого не
замечают: с их точки зрения документ в порядке.

Замер 12 сентября: из одиннадцати собранных файлов **два не открывались** —
`2411-Performance_Up` терял `mv` из `mc:Ignorable`, а
`business-plan-…-creative` терял `v` из `mc:Choice Requires`
(`WORKLOG/2026-09-12-mce-prefixes.md`).

**Что делаем.** При чтении пакета запоминаем все объявления `xmlns:` и при
сериализации возвращаем в корень те префиксы, на которые ссылаются значения
атрибутов MCE, но которых `ElementTree` не объявил. Реализация —
`compose/package.py`, `_restore_mce_prefixes`; регрессия закрыта тестом
`tests/test_mce_prefixes.py`.

**Регистрация префиксов этого не решает.** `ET.register_namespace` влияет только
на то, каким префиксом будет названо используемое пространство имён, и не
заставляет объявить неиспользуемое.
