# Цвет в DrawingML

Самая частая причина, по которой самодельные парсеры показывают неверную палитру.
Три независимых слоя: вид цветового элемента, косвенность через карту цветов,
трансформации.

## §1. Виды цветовых элементов

Внутри любого `a:solidFill`, стопа градиента, обводки или эффекта стоит ровно
один из:

| Элемент | Значение |
|---|---|
| `<a:srgbClr val="4472C4"/>` | прямой RGB в hex |
| `<a:schemeClr val="accent1"/>` | ссылка на роль в схеме, **через карту цветов** — §2 |
| `<a:sysClr val="windowText" lastClr="000000"/>` | системный цвет; берём `lastClr` |
| `<a:prstClr val="red"/>` | именованный цвет из фиксированной таблицы |
| `<a:scrgbClr r="50000" g="50000" b="50000"/>` | компоненты в тысячных долях процента |
| `<a:hslClr hue="…" sat="…" lum="…"/>` | HSL; `hue` в 60000-х долях градуса |

## §2. Косвенность: `schemeClr` не равен роли темы

`<a:schemeClr val="tx1"/>` **не означает** `dk1` из темы напрямую. Между ними
карта цветов мастера:

```xml
<p:clrMap bg1="lt1" tx1="dk1" bg2="lt2" tx2="dk2"
          accent1="accent1" … hlink="hlink" folHlink="folHlink"/>
```

Макет и слайд могут переопределить карту через `p:clrMapOvr`: либо
`<a:masterClrMapping/>` — наследовать мастера, либо `<a:overrideClrMapping …/>`
с полным набором атрибутов.

Порядок разрешения:

```
schemeClr val="tx1"
   → clrMapOvr слайда, если это overrideClrMapping
   → иначе clrMapOvr макета, если это overrideClrMapping
   → иначе clrMap мастера
   → получили имя роли темы, например "dk1"
   → ищем в a:clrScheme темы
```

Отдельно: значения `val="phClr"` встречаются внутри `fmtScheme` и означают
«цвет, переданный извне через `fillRef`/`lnRef`». Разрешаются в момент
применения стиля, а не при чтении темы.

Роли схемы темы: `dk1 lt1 dk2 lt2 accent1..accent6 hlink folHlink`.
Роли карты слайда: `bg1 tx1 bg2 tx2 accent1..accent6 hlink folHlink`.
Имена разные, и это не опечатка — именно поэтому карта и нужна.

## §3. Трансформации

Дочерние элементы цветового элемента, применяются **в порядке появления**.
Значения — в тысячных долях процента: `val="60000"` это 60%.

| Элемент | Что делает |
|---|---|
| `a:lumMod` | умножает светлоту: `L' = L · val` |
| `a:lumOff` | прибавляет к светлоте: `L' = L + val` |
| `a:shade` | затемняет в линейном RGB: `c' = c · val` |
| `a:tint` | осветляет в линейном RGB: `c' = c · val + (1 − val)` |
| `a:satMod` | умножает насыщенность |
| `a:hueMod` | умножает тон |
| `a:alpha` | задаёт прозрачность абсолютно |
| `a:alphaMod` | умножает прозрачность |

`lumMod`/`lumOff` работают по светлоте HSL. `shade`/`tint` — по линейному RGB,
то есть с гамма-коррекцией: `linear = ((s + 0.055) / 1.055)^2.4` для `s > 0.04045`,
иначе `s / 12.92`; обратно `s = 1.055 · linear^(1/2.4) − 0.055`.

Пропуск гамма-коррекции — типичная ошибка: цвета получаются заметно светлее
правильных.

## §4. Что означают варианты цвета в интерфейсе PowerPoint

Полезно, потому что в реальных шаблонах встречается почти только это:

| Подпись в интерфейсе | XML |
|---|---|
| Светлее 80% | `lumMod 20000` + `lumOff 80000` |
| Светлее 60% | `lumMod 40000` + `lumOff 60000` |
| Светлее 40% | `lumMod 60000` + `lumOff 40000` |
| Темнее 25% | `lumMod 75000` |
| Темнее 50% | `lumMod 50000` |

## §5. Где цвет встречается

- `a:solidFill` — сплошная заливка фигуры или текста
- `a:gradFill/a:gsLst/a:gs` — стопы градиента, у каждого свой цвет и позиция
- `a:ln/a:solidFill` — обводка
- `a:effectLst` — тени и свечения
- `p:bg/p:bgPr` — прямой фон слайда
- `p:bg/p:bgRef idx="…"` — фон по ссылке в `bgFillStyleLst` темы, **с `idx` от 1001**
- `p:style/a:fillRef|lnRef|effectRef|fontRef` — стиль фигуры по ссылке в теме

Индексы ссылок на `fmtScheme` начинаются с единицы, а для фоновых заливок — с
1001. То есть `bgRef idx="1001"` — это первый элемент `bgFillStyleLst`.

## §6. Как считаем палитру шаблона

Тема говорит, что *объявлено*. Слайды говорят, что *используется*. Это разные
вещи, и в артефакт идут все три списка:

- `palette.theme[]` — роли схемы, разрешённые в `#RRGGBB`, **по двенадцать на
  каждый мастер**, и у каждой записи есть поле `master`;
- `palette.observed[]` — все цвета, реально встреченные на слайдах, после полного
  разрешения косвенности и трансформаций, с частотой употребления и указанием,
  к какой роли темы они восходят;
- `palette.core[]` — та часть встреченного, которая и есть дизайн-система.

Именно `observed` показывает настоящий визуальный язык шаблона: в теме может быть
шесть акцентов, а использоваться два.

**Двенадцать ролей — это на мастер, а не на файл.** Здесь до 19 сентября стояло
просто «двенадцать ролей схемы», и это неверно: мастеров бывает несколько, у
каждого своя тема (`DOM-PKG §4`), и списки складываются. Замер по корпусу из
одиннадцати шаблонов — 12, 24 или 36 записей; больше двенадцати у трёх файлов из
одиннадцати. Код собирает палитру в цикле по `deck.masters` и проставляет
`master` каждой записи, так что ошибка была только в этом документе. Читатель,
который возьмёт `theme[0..11]` как «палитру шаблона», на таком файле получит
палитру первого мастера и не заметит этого.

### Ядро палитры: чем `core` отличается от `observed`

`observed` — всё, что встретилось, включая цвета векторных иллюстраций. Их бывает
много, и дизайн-системой они не являются: на `stilnyj-shablon` встреченных цветов
**216**. Показывать эксперту 216 плашек бессмысленно, поэтому рядом лежит `core`.

Цвет попадает в ядро, если верно **хотя бы одно** из пяти:

1. он восходит к роли темы;
2. он встречается **не меньше чем на двух** слайдах;
3. им набран текст;
4. им залит фон слайда;
5. он занимает **не меньше 1/50 площади холста** хоть на одной фигуре.

Сверху — потолок в 24 цвета, порядок тот же, что в `observed`: по убыванию
частоты, при равенстве по hex. Реализация — `tokens.py`, `_observed_palette`.

Потолок не декоративный: на том же `stilnyj` 216 наблюдённых сжимаются ровно до
24, на `svetlaja-tema` 43 → 12. На девяти остальных файлах корпуса ядро равно
наблюдённому у семи, и меньше на один и на четыре цвета у двух. То есть правило
отбора работает в основном на «грязных» шаблонах, ради которых и вводилось, а
чистый шаблон проходит его насквозь.

## §7. Округление: почему наш цвет отличается от PowerPoint на единицу

Преобразование в HSL и обратно неизбежно теряет точность, и PowerPoint округляет
иначе, чем `colorsys`. На практике расхождение — не более единицы по каналу.

Проверено на «Accent 1, светлее 40%» от `#4472C4` (`lumMod 60000` + `lumOff 40000`):

| | R | G | B |
|---|---|---|---|
| PowerPoint | 142 | 169 | 219 (`#8EA9DB`) |
| наш расчёт | 143 | 170 | 220 (`#8FAADC`) |

Для наших задач это неважно: цвет используется для сборки палитры и для
подстановки в тот же `schemeClr` с теми же трансформациями, то есть в готовом
файле PowerPoint посчитает его сам и получит своё значение. Гнаться за точным
совпадением незачем — но тесты сравнивают с допуском, а не по равенству
(`tests/test_color.py::test_lum_mod_off_matches_powerpoint_lighter_40`).
