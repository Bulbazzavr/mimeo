# Текст и типографика

## §1. Структура текстового тела

```
p:txBody
  ├─ a:bodyPr        поля, привязка, перенос, автоподбор
  ├─ a:lstStyle      стили уровней списка для этой фигуры
  └─ a:p             абзац
       ├─ a:pPr      свойства абзаца, в т.ч. a:defRPr — умолчание для прогонов
       ├─ a:r        прогон
       │    ├─ a:rPr свойства прогона
       │    └─ a:t   текст
       ├─ a:br       разрыв строки
       ├─ a:fld      поле (номер слайда, дата)
       └─ a:endParaRPr свойства «пустого» конца абзаца
```

Текст слайда — это `a:t` внутри `a:r`. Текст внутри `a:fld` тоже отображается, но
он вычисляемый и в контент не идёт.

**Порядок детей `a:p` задан схемой и соблюдается буквально:**

```
a:pPr?            свойства абзаца, если есть — строго первым
(a:r | a:br | a:fld)*   прогоны, разрывы и поля, в порядке чтения
a:endParaRPr?     если есть — строго последним
```

Грабли, стоившие дня 12 сентября. Пустой абзац макета состоит **ровно из одного**
`a:endParaRPr`. Подстановка добавляла прогон в конец элемента — то есть **после**
него. XML остаётся синтаксически корректным, схема нарушается, и PowerPoint
считает абзац законченным на `a:endParaRPr`, а прогон игнорирует: **текст лежит в
файле и не отображается, слайд выходит пустым листом**.

Ни `python-pptx`, ни наш разбор этого не видят — оба читают `a:t` где бы он ни
стоял. Видно только в самом PowerPoint. Наблюдалось на трёх шаблонах корпуса, где
паттерны выведены из макетов (`ADR-0006`); разбор — `WORKLOG/2026-09-12-endpararpr.md`,
регрессия — `tests/test_paragraph_order.py`.

Практическое следствие: **новый прогон вставляется перед `a:endParaRPr`, а не
дописывается в конец.** И шире — при правке `a:p` порядок детей надо держать, а
не полагаться на то, что читатели терпимы.

## §2. Цепочка наследования свойств прогона

Восемь уровней, сверху вниз — от самого сильного:

1. `a:rPr` самого прогона
2. `a:pPr/a:defRPr` его абзаца
3. `a:lstStyle/a:lvlNpPr/a:defRPr` этой же фигуры, где N — уровень абзаца (`lvl`, по умолчанию 0 → `lvl1pPr`)
4. соответствующий плейсхолдер **макета**: сопоставление по `idx`, если его нет — по `type`
5. соответствующий плейсхолдер **мастера**
6. `p:txStyles` мастера — по типу плейсхолдера:
   - `p:titleStyle` для `title` и `ctrTitle`
   - `p:bodyStyle` для `body`, `subTitle`, `obj`
   - `p:otherStyle` для остального, включая свободные текстовые блоки
7. `p:defaultTextStyle` из `presentation.xml`
8. `a:fontScheme` темы для токенов гарнитуры

Свойства разрешаются **по одному**: кегль может прийти с уровня 1, цвет с
уровня 5, гарнитура с уровня 8. Нельзя взять первый непустой `rPr` целиком.

## §3. Гарнитура

```xml
<a:latin typeface="+mj-lt"/>   мажорная латиница из темы
<a:latin typeface="+mn-lt"/>   минорная латиница из темы
<a:latin typeface="Golos Text"/>  явная гарнитура
```

Плюс `a:ea` для восточноазиатских и `a:cs` для комплексных письменностей.
Токены `+mj-lt` / `+mn-lt` разрешаются в `a:fontScheme/a:majorFont/a:latin` и
`…/a:minorFont/a:latin` темы.

Для кириллицы важно: в `a:fontScheme` есть блоки `a:font script="Cyrl"`, которые
подменяют гарнитуру для конкретной письменности. Если они есть — для русского
текста действует именно эта гарнитура, а не `a:latin`.

## §4. Единицы

| Атрибут | Единица | Пример |
|---|---|---|
| `sz` | сотые доли пункта | `sz="1800"` = 18 pt |
| `spc` | сотые доли пункта, трекинг | `spc="-25"` = −0.25 pt |
| `a:lnSpc/a:spcPct val` | тысячные доли процента | `val="90000"` = 90% |
| `a:lnSpc/a:spcPts val` | сотые доли пункта | `val="1500"` = 15 pt |
| `a:spcBef`, `a:spcAft` | так же, как `lnSpc` | |
| `marL`, `indent` | EMU | `marL="342900"` |
| `b`, `i`, `u` | булево `1`/`0` | |
| `cap` | `none` \| `small` \| `all` | |

## §5. Автоподбор — критично для оценки вместимости

В `a:bodyPr` ровно один из трёх:

```xml
<a:noAutofit/>                          не подгонять, текст вылезет
<a:spAutoFit/>                          подгонять фигуру под текст
<a:normAutofit fontScale="70000"
               lnSpcReduction="20000"/> уменьшать текст под фигуру
```

**Главное.** `fontScale` и `lnSpcReduction` **уже посчитаны PowerPoint** и
записаны в файл. Значит эффективный кегль прогона равен

```
sz_эфф = sz · fontScale / 100000
```

Если это не учесть, извлечённая типографическая шкала окажется завышенной: в
файле написано 24 pt, а на экране 16.8 pt. Это же значение — сигнал, что автор
шаблона запихнул в блок больше текста, чем тот вмещает.

**То же самое через COM, и на этом легко ошибиться.** `TextRange.Font.Size`
отдаёт **видимый** кегль, то есть уже со шкалой: 16 pt при `fontScale="62000"`
приходит как 10. Проверено замером 12 сентября. Кто считает от этого числа
предел читаемости, обязан сначала восстановить номинал — иначе предел съезжает с
каждым раундом ремонта, а его присвоение однажды даже поднимает шкалу обратно к
сотне. Оба дефекта были и исправлены (`mimeo/verify/repair.py`,
`WORKLOG/2026-09-12-repair.md`).

## §6. Поля текстового блока

Умолчания `a:bodyPr`, если атрибут не задан:

| Атрибут | Умолчание, EMU | В дюймах |
|---|---|---|
| `lIns` | 91440 | 0.1 |
| `tIns` | 45720 | 0.05 |
| `rIns` | 91440 | 0.1 |
| `bIns` | 45720 | 0.05 |

Плюс `anchor` (`t` \| `ctr` \| `b`), `anchorCtr`, `wrap` (`square` \| `none`),
`rot` — поворот текста отдельно от поворота фигуры.

Полезная ширина строки = ширина фигуры − `lIns` − `rIns`. Отсюда считается
вместимость слота, которой стадия PLAN ограничивает LLM (`ADR-0002`).

## §7. Как выводим типографическую шкалу

Не из `p:txStyles` мастера. Причина: в реальных шаблонах мастер и слайды
расходятся, а видит эксперт слайды.

Порядок: собрать все прогоны со всех слайдов с **полностью разрешёнными**
свойствами (§2) и с учётом `fontScale` (§5), затем кластеризовать по кортежу
(гарнитура, кегль, начертание, регистр, цвет) и приписать роли по эвристикам:
самый крупный в верхней трети холста — заголовок; самый частый — тело; мелкий
под крупным — подпись и так далее. Наблюдаемый набор кеглей и есть шкала
шаблона: её нельзя округлять к «красивой» прогрессии.

## §8. Число на слайде разрезано на несколько прогонов

Признак «это большое число» нельзя считать на уровне прогона. PowerPoint режет
одно визуальное число на несколько `a:r`: знак валюты, само число и подпись
нередко оказываются отдельными прогонами одного абзаца, потому что автор в
какой-то момент выделил часть текста.

Замерено на трёх реальных шаблонах, доля «текст целиком является числом»:

| Кластер | По прогонам | По фигурам | Что это на самом деле |
|---|---|---|---|
| Arial 72 pt | 50% | **100%** | настоящая метрика: `89,526,124`, `$100%`, `185,244` |
| Arial 48 pt | 50% | **0%** | заголовки с нумерацией: `1.TRANSITION HEADLINE` |
| Lato Bold 100 pt | 100% | 100% | номера разделов: `04`, `05`, `06` |
| Segoe UI 48 pt | 60% | 60% | смесь: `GET STARTED`, `$899` |

По прогонам два первых кластера неразличимы — оба дают 50%. По фигурам они
расходятся на весь диапазон. Вывод: **признак считается по тексту, собранному в
пределах одной фигуры**, а порог ставится на 0.8.

Тот же вывод шире: «метрика» — свойство не начертания, а блока. Типографическая
роль отвечает на вопрос «каким шрифтом набрано», а не «что этим набрано».

## §9. Как оценивается вместимость блока

Полное решение требует метрик шрифта, которых у нас нет. Работающее приближение:

```
полезная_ширина = cx − lIns − rIns                     (§6)
ширина_знака    = кегль · 12700 · em
знаков_в_строке = полезная_ширина / ширина_знака
высота_строки   = кегль · 12700 · интерлиньяж
строк           = (cy − tIns − bIns) / высота_строки
вместимость     = знаков_в_строке · строк · 0.92
```

Средняя ширина знака `em` в долях кегля:

| Набор | em |
|---|---|
| смешанный, латиница и кириллица | 0.52 |
| прописными (`cap="all"`) | 0.66 |
| полужирный | ×1.03 |

Коэффициент 0.92 — скидка на то, что строки рвутся по словам и правый край
недоиспользуется. При `wrap="none"` строка всегда одна, сколько бы ни было
места по высоте. Интерлиньяж берётся из `a:lnSpc`, а **когда его нет — 1.2**;
это единственная величина формулы, которая не читается из файла.

Кроме `max_chars` считаются ещё два числа, и они не про геометрию:

- `target_chars` — **донор × 1.6**, но не больше `max_chars`. Это не предел, а
  ориентир: донор с заголовком в 20 знаков означает «примерно столько», а не
  «ровно столько». Модели показывают оба числа;
- `max_items` — сколько пунктов списка уместно, от числа пунктов у донора
  плюс два. Считается только когда у донора пунктов больше одного.

Всё это — `mimeo/analyze/fitting.py`, функция `estimate`.

**Чего стоит это приближение — измерено 12 сентября.** Флаг `over_capacity`,
который ставится по формуле выше, сверили с габаритами текста от самого
PowerPoint на корпусе из одиннадцати шаблонов, **97 слотов**:

| | текст влезает | текст переполняет |
|---|---|---|
| оценка предупредила | 9 | 12 |
| оценка промолчала | 55 | **21** |

**Полнота 36%** — из трёх настоящих переполнений находится одно. **Точность
57%** — четыре тревоги из десяти ложные. Ошибается в обе стороны сразу, поэтому
подкрутить коэффициенты нельзя: приближение таково по устройству.

Практический вывод: формула годится, чтобы **подсказать, где будет тесно**, и
негодна, чтобы на ней строить решение. Кто знает правду — движок вёрстки
(`ADR-0014`), и спрашивать надо его. Числа — `WORKLOG/2026-09-12-overflow-truth.md`.

*Здесь до 19 сентября стояло «123 слота». Замер сделан на 97 — столько их и в
таблице выше (9 + 12 + 55 + 21), из них переполняется 33, и 36% с 57% считаются
именно отсюда. Число 123 настоящее, но из другого замера, сделанного позже и уже
с детектором: `WORKLOG/2026-09-12-detector.md`, 123 слота и 37 переполнений по
высоте. Два соседних замера по одному корпусу дали разные знаменатели, и чужой
переехал сюда — тот самый случай, о котором предупреждает `CLAUDE.md` историей
про «подставлено 123 из 123».*

### Дополнено 17 сентября: оценка и замер отвечают на разные вопросы

Вывод выше — «формула негодна, чтобы на ней строить решение» — **оказался слишком
широким**, и это выяснилось дважды за два дня.

**Случай, где права была оценка, а не замер.** На слайде 2 колоды по выданному
шаблону VK WorkSpace три заголовка карточек уезжали под тёмную плашку — дефект
виден глазом. Наша формула переполнение **видела**: отношение знаков к ёмкости
1.38, 1.90, 1.91. Детектор от движка вёрстки (`ADR-0015`) не увидел **ничего** и
сообщил «переполнено 3 → 0», починив другие слайды
(`WORKLOG/2026-09-16-scales-vs-eye.md`).

Причина не в том, что один измеритель лучше. **Они отвечают на разные вопросы:**

| Измеритель | Вопрос |
|---|---|
| формула §9 | влезает ли текст в слот, **каким его задумал дизайнер** |
| детектор от движка | **сталкивается** ли набранный текст с чем-нибудь |

Текст, помещающийся в свой бокс и при этом пересекающий чужую декоративную
плашку, второму вопросу не противоречит, а первому — да. **Зритель ближе к
первому.**

**Где мы теперь строим на оценке и почему это не противоречит выводу выше.**
Весы колоды (`ADR-0019`, `mimeo/plan/quality.py`) считают на ней две ступени —
«сломано безвозвратно» и «переполнено, но поправимо». Разница с запрещённым
употреблением в двух вещах:

1. **Весы сравнивают варианты между собой, а не объявляют дефект пользователю.**
   Систематическая ошибка формулы одинакова для всех вариантов и при сравнении
   сокращается; для абсолютного суждения она бы осталась.
2. **Ступень «сломано» — это не «текст не влезает», а «ремонт уже не спасёт»:**
   к отношению из формулы добавлен пол читаемости из `repair.py`. Формула здесь
   отвечает на вопрос о будущем ремонте, а не о текущем виде.

Вывод §9 в силе для того, для чего он писался: **сказать пользователю «здесь
дефект» на одной формуле нельзя.** Сравнивать ею варианты — можно, и это
измерено (`WORKLOG/2026-09-16-scales-baseline.md`).

**Оценка не может быть меньше того, что уже написано в доноре.** Донор — слайд,
сделанный дизайнером; текст в нём заведомо помещается. Без этой проверки
геометрическая формула на плотно свёрстанной плашке выдаёт «влезает 1 знак» для
блока, в котором стоит двузначное число. Обоснование — `ADR-0008`.

## §10. Пустое имя гарнитуры в теме — это норма, а не дефект

`PowerPoint` показывает в `Presentation.Fonts` безымянную запись, и десять дней
это числилось загадкой (`OQ-13`): откуда в собранном файле ссылка на шрифт с
пустым именем, которой «нет в шаблоне».

**Проверено 19 сентября сравнением XML шаблона и нашего файла.** Пустые
`typeface` есть **в самом шаблоне**, в `ppt/theme/theme1.xml`:

```xml
<a:ea typeface=""/>
<a:cs typeface=""/>
```

Их ровно двенадцать — в `majorFont` и `minorFont` темы, для восточноазиатского
письма (`a:ea`) и сложных систем письма (`a:cs`). В нашем файле их **столько
же**: клон несёт тему шаблона как есть и ни одной записи не добавляет.

Пустой `typeface` в этих элементах — штатная запись стандарта: «гарнитура для
этой письменности не задана, взять подстановку системы». Office так и пишет
темы по умолчанию.

**Вывод для кода:** искать здесь нечего и чинить нечего. Если счётчик шрифтов в
отчёте когда-нибудь понадобится показывать человеку, безымянные записи темы
стоит из него исключать — но это косметика отчёта, а не дефект пакета.

Тот же случай, что и три тревоги 12 сентября: прежде чем чинить, проверить, что
это вообще дефект.


## §11. Как узнать, что гарнитура моноширинная

Коротко: **по имени, и другого способа у нас нет.** Оба родных признака OOXML
проверены по четырнадцати шаблонам и оказались негодны.

У `<a:latin>` есть два необязательных атрибута, которые по стандарту описывают
шаг и пропорции гарнитуры:

* `pitchFamily` — байт `LOGFONT.lfPitchAndFamily` Windows: младшие два бита это
  шаг, `1` = фиксированный;
* `panose` — десять байтов классификации PANOSE; четвёртый байт,
  `bProportion`, при значении `9` означает «моноширинный».

Замер 20 сентября, все четырнадцать шаблонов
(`WORKLOG/2026-09-20-z43-baseline.md`, замер 4):

| Гарнитура | Шаблон | `pitchFamily` | Шаг по нему | Правда |
|---|---|---|---|---|
| `Consolas` ×210 | VK Tech | **нет** | — | моноширинная |
| `Consolas` ×132 | VK Education | **нет** | — | моноширинная |
| `Courier New` ×29 | 2411 | 92 | 0, не фиксированный | **моноширинная** |
| `Monaco` ×1 | 2411 | 92 | 0, не фиксированный | **моноширинная** |
| `Arial` ×8 | 2411 | 25 | **1, фиксированный** | **пропорциональная** |
| `Times New Roman` ×6 | 2411 | 25 | **1, фиксированный** | **пропорциональная** |

**Атрибута нет там, где он нужен, и он врёт там, где есть.** Ни один из шести
случаев не отвечает правде. `panose` не записан в корпусе вовсе ни для одной
моноширинной гарнитуры.

Причина понятная: оба атрибута пишет тот редактор, который создал файл, из своей
системной таблицы шрифтов. Шрифта нет в системе — атрибута нет или он от
подстановки. Стандарт их не требует и не проверяет.

**Что делаем вместо.** Имя гарнитуры режется на слова — по разделителям и по
горбатому регистру, — и слово сверяется со списком (`config/typography.json`):
`mono`, `code`, `courier`, `console`, `typewriter`. Отдельно перечень имён, чьё
написание не намекает: `Consolas`, `Monaco`, `Menlo`, `Inconsolata`, `Hack`,
`Iosevka`, `Terminal`.

Сверка **по целому слову**, а не по подстроке: иначе `Monotype Corsiva` станет
моноширинной. И `Terminal` именно в перечне точных имён, а не в токенах: есть
рубленый `Terminal Dosis`.

По всем 86 именам гарнитур корпуса правило срабатывает ровно на четырёх
настоящих и ни на одном лишнем (замер 8 там же).

**Метрики глифов не годятся:** файлов шрифтов у нас нет, ширины знаков считать
не по чему (§9). Признак считается **по фигуре**, как и всё прочее здесь (§8).

## §12. Пиктограммные гарнитуры узнаются по тексту, а не по имени

Шрифт-пиктограммы (`FontAwesome`, `linecons`, `Glyphicons`) кладёт свои знаки в
**область частного использования** Unicode: U+E000–U+F8FF в основном плане и
планы 15–16 целиком. Текст такой фигуры из неё и состоит:

```
'    …'     linecons 83 pt, business_plan.pptx, слайд 19
''                            FontAwesome 24 pt, stilnyj-shablon
```

Поэтому здесь имя не нужно: доля знаков области частного использования среди
непробельных ≥ 0.5 — гарнитура пиктограммная. Правило не зависит ни от имени, ни
от языка, ни от версии шрифта.

**Чего оно не ловит:** старый класс шрифтов, сидящий на ASCII, — `Wingdings`,
`Webdings`, `Symbol`. Там буква `J` рисуется улыбкой, и текст от обычного не
отличить. Этот класс добирается перечнем имён, и предел записан здесь честно, а
не замазан.

## §13. Якорь и угол набранного текста через COM

Зонд VERIFY спрашивает у PowerPoint не разметку, а результат вёрстки, и два
значения там устроены не так, как в OOXML.

**Номера якоря — `MsoVerticalAnchor`, а не порядок атрибута `anchor`.**
`TextFrame2.VerticalAnchor` отдаёт 1 — верх, **3 — середина, 4 — низ**; 2 и 5 —
верх и низ по базовой линии. В разметке у `a:bodyPr/@anchor` значения `t`,
`ctr`, `b`, `just`, `dist`, и перенести их порядок на числа COM — ошибка,
которую код VERIFY сделал 13 сентября и носит до сих пор (`Z-54`). Проверено
положением набранного текста: у якоря 3 он стоит точно посередине бокса у 478
надписей, у якоря 4 — точно по низу у 165.

**Настоящий угол набранного текста — `TextRange2.BoundLeft` и `BoundTop`.** Угол
бокса плюс поле совпадает с ним только у якоря «верх» и левого выравнивания:
у середины и низа расходится больше чем на 2 пт у 52 из 56 и 19 из 21 надписи
на девяти сдаточных колодах, по горизонтали — у 91 из 382. У якоря «верх» они
совпадают в пределах 1.5 пт у 1839 надписей из 1927; у 86 текст начинается на
2.7–3.5 пт ниже угла, причина поимённо не разобрана.

**У повёрнутой фигуры** `Bound*` — охватывающий прямоугольник набранного текста
**на слайде**, а не в осях фигуры: у поворота на 90° это 9.6 × 55 пт при боксе
101 × 13. Поворот фигуры — `Shape.Rotation`, 0…360; ровно стоящие фигуры
отдают и 359.93, и 359.99.

Наблюдалось на 14 шаблонах и 20 колодах, `WORKLOG/2026-09-23-z53-baseline.md`,
§ 8.1, 8.4, 8.5.

## §14. Встроенный, но не установленный шрифт: замер и отрисовка расходятся

Наблюдалось 27 сентября на всех трёх выданных шаблонах (гарнитура Play, в
системе не установлена) — растр сдаточной девятки против замера VERIFY.

- `Presentation.Fonts` называет Play **встроенным** (`Embedded = -1`).
- Объектная модель (`TextRange.Lines`, `BoundHeight`) раскладывает текст по
  метрикам встроенного Play: «Выдуманное / число колоду / не пропустит» —
  3 строки, 208 пт.
- Отрисовка — `Slide.Export` в PNG и сохранение в PDF — рисует **Arial** (в PDF
  лежат `ArialMT` и `Arial-BoldMT`) и переносит по его метрикам:
  «Выдуманное / число / колоду не / пропустит» — 4 строки, текст за краем
  слайда.
- `Presentation.Fonts.Replace("Play", "Arial")` в сеансе замера даёт ровно
  строки растра: 4 строки, 274 пт.

Отсюда правило зонда VERIFY (`mimeo/verify/powerpoint_probe.ps1`): гарнитуру,
которой нет в реестре шрифтов системы и пользователя, мерить заменой Arial —
колода открыта только для чтения, замена живёт в памяти сеанса. Эксперт, у
которого Play тоже нет, увидит отрисовку, а не метрики объектной модели.
