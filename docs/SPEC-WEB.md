## 1. Что это за проект

`mimeo` — движок переноса стиля презентаций. На входе произвольный
`.pptx`-шаблон и текст, на выходе готовая презентация **в стиле этого шаблона**.

Главное отличие от всего, что делают конкуренты: **дизайн не придумывается, а
извлекается из файла**. Слайд не рисуется с нуля — он **клонируется из
настоящего слайда шаблона** с подстановкой содержимого в известные места. Всё,
чего движок не понял — тени, градиенты, декоративная графика, — приезжает вместе
с клоном и выглядит так, как задумал дизайнер.

Движок написан целиком на стандартной библиотеке Python, обязательных
зависимостей ноль. **Колоду по умолчанию строит локальная модель** — нужны
видеокарта и серверы моделей, их ставит `start.bat` (только Windows; на Linux
серверы поднимают своими средствами, `MODELS.md`); с `--llm off` сборка идёт
без модели и без сети. Один и тот же вход при одном и том же ответе модели и
тех же картинках даёт побайтово одинаковый файл на выходе.

Одно исключение, о котором стоит знать заранее: **`jsonschema` подключается
опционально** и только для флага `--validate`. Без неё всё работает, а проверка
по схеме **пропускается с сообщением** — не молча. Если веб-слой захочет
показывать результат проверки артефакта, он обязан различать «схема пройдена» и
«проверить было нечем»: это то же правило, что в разделе 6 про `status`.

**Что прочитать перед началом** — не ради формальности, а потому что на питче
отвечать придётся обоим, а питч это пятая часть оценки:

| Файл | Зачем |
|---|---|
| [`README.md`](../README.md) | что умеет и чего не умеет, честный список ограничений |
| [`ARCHITECTURE.md`](../ARCHITECTURE.md) | пять стадий и границы слоёв |
| [`docs/STATE.md`](STATE.md) | где мы сейчас |
| [`docs/context/04-pitch-notes.md`](context/04-pitch-notes.md) | что мы **вправе утверждать** и чем каждое утверждение подтверждается |

Последний особенно: там перечислено, что можно говорить экспертам, а что нельзя,
и каждое утверждение привязано к замеру.

## 2. Граница, и она архитектурная

**Веб-слой не имеет права затащить зависимости в движок.** Ноль обязательных
зависимостей — это утверждение, которое мы выносим на питч, и оно ломается одним
неосторожным импортом.

Отсюда устройство:

- **отдельный каталог** в репозитории, например `web/`;
- **свои зависимости**, свой `requirements.txt` — движка они не касаются;
- движок виден **только через командную строку**, как его видел бы посторонний
  пользователь;
- **`import mimeo.*` запрещён.** Если веб-слою чего-то не хватает — это чинится
  расширением командной строки, а не импортом в обход границы. Скажите, чего не
  хватает, и я расширю.

Побочная польза: так веб-слой заодно проверяет, что продукт пригоден для
встраивания. Если интерфейс неудобно построить — значит плоха командная строка,
и это стоит узнать до питча, а не на нём.

**Что из этого следует практически:** файлы не пересекаются, конфликтов при
слиянии нет, тесты движка от работы над вебом не падают, и разбираться в движке,
чтобы начать, не нужно.

## 3. Контракт с движком

Всё запускается из корня репозитория. Четыре команды.

### Собрать презентацию

```
python -m mimeo build <шаблон.pptx> <текст.md> -o <каталог> --output <файл.pptx>
```

~~Кладёт на диск **один файл — сам `.pptx`**. Больше ничего.~~

> **Поправка 26 сентября: файлов на диске больше.** Рядом с `.pptx`, в
> каталоге `-o`, всегда ложится `outline.json` — что спросили у модели, что она
> ответила, итог каждой проверки, со статусом (`contracts/outline.schema.json`);
> пишется и тогда, когда модель не звали, чтобы файл прошлой сборки не соврал
> про эту. Нарисованные картинки — в `images/` того же каталога. С `--verify` —
> `render-report.json`, с `--report` — итог сборки, с `--export` — `.html` и
> `.pdf` рядом с колодой.

С флагом `--variants 3` — три варианта вёрстки одного текста, файлы получают
суффикс: `deck-1.pptx`, `deck-2.pptx`, `deck-3.pptx`. Если шаблон беден
раскладками и трёх заметно различных колод из него не выходит, будет собрано
меньше, и причина будет названа в выводе.

Полезные флаги:

| Флаг | Что делает |
|---|---|
| `--slides 10-15` | целевой объём колоды; рамки ТЗ — 10–15 |
| `--variants 3` | три варианта вёрстки |
| `--llm off\|cache\|on` | модель строит колоду: `on` — звать её (умолчание), `cache` — только сохранённые ответы, без сети, `off` — без модели |
| `--text keep\|improve` | что модель делает с текстом: `improve` — переписать короче и яснее (умолчание), `keep` — фразы автора дословно |
| `--images on\|off` | рисовать ли картинки по идеям модели генератором (умолчание — `on`) |
| `--report <файл>` | машинночитаемый итог сборки (`contracts/build-report.schema.json`) |
| `--verify` | проверить вёрстку настоящим PowerPoint и ужать непоместившееся |
| `--rounds N` | сколько раундов ремонта при `--verify` (умолчание — 3) |
| `--export html,pdf` | выгрузить каждую собранную колоду ещё и в `.html` и/или `.pdf` рядом с ней |
| `-q` | без текстовой сводки |
| `--config run.json` | все аргументы одним JSON-файлом |

### Разложить текст, не собирая файл

```
python -m mimeo plan <шаблон.pptx> <текст.md> -o <каталог>
```

Кладёт `<каталог>/deck-plan.json` — **машинночитаемый план колоды**. Это
единственный структурированный ответ, который сегодня можно получить, и пока
он же единственный способ узнать, сколько выйдет слайдов, до сборки.

> **Поправка 26 сентября.** `plan`, как и `build`, по умолчанию зовёт модель и
> кладёт рядом `outline.json`; итог самой сборки даёт `build --report`
> (раздел 4), так что «единственный» здесь — уже не так.

Форма (проверено на реальном прогоне):

```json
{
  "version": "1.2",
  "source": { "content": "...", "design_system_sha256": "...",
              "patterns_sha256": "...", "configs": [ ... ] },
  "slides": [ { "index": 0, "pattern_id": "p03", "fills": [ ... ],
                "reason": "...", "origin": { ... } } ],
  "diagnostics": { "planner": "deterministic", "unplaced": [], "warnings": [ ... ] }
}
```

Что отсюда стоит показывать:

- `slides` — сколько слайдов и какая раскладка у каждого;
- `diagnostics.unplaced` — **куски текста, которым не нашлось места**. Список
  должен быть виден: молча потерянный текст хуже честного отказа;
- `diagnostics.warnings` — человекочитаемые предупреждения, их можно выводить
  как есть.

Схема лежит в [`contracts/deck-plan.schema.json`](../contracts/deck-plan.schema.json)
и проверяется тестами — форма не поменяется молча.

### Разобрать шаблон

```
python -m mimeo analyze <шаблон.pptx> -o <каталог>
```

Кладёт `design-system.json` (палитра, типографика, сетка) и `patterns.json`
(библиотека раскладок). Пригодится, если захочется показать «вот что система
вынула из вашего шаблона» — это сильный экран для демо и он не требует запуска
генерации.

### Выгрузить колоду в `.html` и `.pdf`

```
python -m mimeo export <колода.pptx> --html --pdf -o <каталог>
```

> **Добавлено 26 сентября** (`Z-27`, `PLAN-10.0`). Без `--html` и `--pdf` —
> оба формата; без `-o` — рядом с колодой, с тем же именем. HTML — свой рендер
> пакета, ему не нужны ни PowerPoint, ни LibreOffice; PDF рисует PowerPoint
> (Windows), иначе LibreOffice.
> Печатает по строке на формат: путь, число слайдов или страниц, чем рисовали и
> что пришлось упростить.

### Коды возврата

Сверены с `mimeo/cli.py` и прогоном 26 сентября:

| Код | Значение |
|---|---|
| `0` | всё хорошо; у `export` — собраны все форматы |
| `1` | ошибка входа: файла нет, пакет или XML внутри него битый; значение, которое проверяет сам движок, — например `--slides abc`; у `export` — хоть один формат не собран |
| `2` | отработало, но **есть проблемы**: у `build` — структурные замечания в собранном файле, у `analyze` и `plan` с `--validate` — артефакт не прошёл схему. **Тот же код даёт сам `argparse`** на неизвестный флаг или значение не из списка (`--llm maybe`) — тогда не собрано ничего |
| `3` | у `export`: PowerPoint открыт у пользователя, PDF не сделан — попросить закрыть |

**`2` у `build` — не ошибка.** Файл собран и его можно отдавать; интерфейс
должен показать проблемы, а не прятать результат. Отличить его от ошибки
разбора аргументов проще всего по отчёту `--report`: он есть — сборка дошла
до конца (так и судит `web/serve.py`). **Неустранённая вёрстка код возврата не
меняет:** отказ ужимать ниже предела читаемости — штатный исход, он в отчёте
проверки, а не в коде.

**Вы встретите `2` сразу и без `--verify`:** на `svetlaja-tema-…` обычная
сборка даёт структурное замечание в собранном файле (перепроверено 26 сентября
путём без модели). Если интерфейс покажет здесь «ошибка, повторите» вместо
готовой презентации с пометкой, он соврёт.

### Отчёт проверки вёрстки

С флагом `--verify` появляется `<каталог>/render-report.json`. С
`--variants` — `render-report-1.json`, `-2`, `-3`.

```json
{ "version": "1.2", "deck": "...", "status": "ok", "stopped": "floor",
  "defects": { "before": 8, "after": 4 },
  "unresolved": [ { "slide": 4, "slot": "s05", "kind": "overflow_height",
                    "ratio": 1.385, "role": "body", "shape": "714" } ],
  "occluded":   [ { "slide": 7, "slot": "s06", "role": "label",
                    "shape": "1126", "share": 0.68 } ],
  "overflow_width": [ { "slide": 3, "slot": "s01", "role": "title",
                        "shape": "42", "ratio": 1.94 } ],
  "donor_overflow": [],
  "rounds": [ ... ], "seconds": 18.1, "note": "" }
```

Два поля решают всё, и о них отдельный разговор в разделе 6:

| Поле | Значения | Что означает |
|---|---|---|
| `status` | `ok` | замер состоялся |
| | `not_measured` | замер **не состоялся** |
| | `unavailable` | мерить нечем: нет Windows или Office |
| `stopped` | `fits` | ремонту больше нечего чинить: переполнений **по высоте** и, с 26 сентября, слов, разорванных посередине строки (`Z-56`), не осталось. Ширина, донор и заслонения при этом остаться могли — они в своих списках |
| | `floor` | упёрлись в предел читаемости — сделано всё, что можно |
| | `rounds` | кончились раунды ремонта |
| | `not_measured`, `unavailable` | как у `status`: замера не было |

**`defects` и `unresolved` — это чинимое:** переполнение по высоте (`kind:
overflow_height`) и, с 26 сентября, разорванное слово (`broken_word`, `Z-56`).
Версия схемы та же, `1.2`: новый вид — новое значение в открытом списке видов.

**`occluded` появился 20 сентября (`Z-47`) и устроен иначе, чем `unresolved`.**
Это надписи, закрытые непрозрачной фигурой, лежащей **поверх** них. Ремонтом
они не чинятся вовсе — текст в боксе переносится, и меньший кегль не уводит
строку из-под картинки, — поэтому в `defects.before/after` они **не входят** и
списком идут отдельно.

И поле там другое: `share` — **доля закрытого текста от 0 до 1**, а не
кратность превышения, как `ratio` у переполнений. В интерфейсе это разные
шкалы: `ratio: 1.38` значит «в 1.38 раза выше места», `share: 0.68` значит
«две трети текста не видно».

Список необязательный: старые отчёты его не содержат, и версия схемы из-за него
не поднималась (правило 3 `ARCH-CONTRACTS`).

**`overflow_width` и `donor_overflow` появились 22 сентября (`Z-52`).** Это
наши надписи **шире своего места** и переполненные **фигуры донора** — те, куда
мы ничего не подставляли. Оба поимённо и по **итоговой** колоде, как
`occluded`, и оба в `defects.before/after` не входят: ремонт берёт высоту и
разорванное слово, а не ширину. До того их не было в отчёте вовсе, а печатная сводка звала всю ширину
«донорской» — на корпусе это были **наши надписи, 27 из 27**. **Считать их
самим из `rounds` нельзя:** раунды не видят итоговой колоды, и это не
предположение — у WorkSpace, вариант 3, по раундам ноль, в итоге одна. Списки
необязательные; их нет — число неизвестно, а не ноль.

**С 21 сентября движок такие надписи не чинит, а старается не допускать**
(`Z-48`): ёмкость слота считается по его **видимой** полосе, и заслонённый слот
не получает запаса на переполнение. Для интерфейса это значит две вещи. Список
стал короче, но **не обязан быть пустым** — оставшиеся случаи ёмкостью не
чинятся и показывать их надо по-прежнему. И в `patterns.json` у слота появилось
необязательное поле `visible_rect_emu` — та самая полоса, а у паттерна список
`opaque`: непрозрачные куски декора донора. Оба поля печатаются, только когда
есть что печатать; версия схемы не поднималась по тому же правилу 3.

## 6. Правила, нарушение которых испортит сдачу

### «Проверить не смогли» и «дефектов нет» — разные вещи

Это главное правило проекта, и оно оплачено дорого. Однажды измеритель отказал и
вернул пустоту, а мы прочли её как «чисто». В контракте отчёта оно закодировано:
поле `status` **обязательно и проверяется первым**.

```
status == "ok"          -> defects.after можно показывать — и только вместе с
                           длинами occluded, overflow_width, donor_overflow
status != "ok"          -> показать «проверить не смогли» и причину
```

**Одно `defects.after` — неполная правда.** Это переполнения по высоте и
разорванные слова — то, что чинит ремонт. Показанное без трёх списков рядом,
оно и есть та «сводка по одному `ours`», что соврала бы «дефектов нет»
(`ARCH-CONTRACTS`). На `prostoj-shablon` это «1 → 0» при тринадцати надписях
шире своего места (`Z-52`). И у самой проверки есть слепое пятно — **строки
одной надписи друг на друге** (`Z-55`); пока оно не закрыто меркой, ноль не
показывается как успех. Два других пятна закрыты: наложение текста на соседний
текст, когда боксы шаблона перекрываются (`Z-53`), — 23 сентября, **слово,
разорванное посередине строки** (`Z-56`), — 26 сентября: проверка его видит,
ремонт ужимает кегль.

Пустой список дефектов при `status != "ok"` означает **«не проверяли»**, а не
«всё хорошо». Интерфейс, показывающий в этом случае зелёную галочку, врёт
пользователю.

То же самое про `stopped`: `floor` значит «сделано всё, что можно».

**`rounds` какое-то время доверять было нельзя, и это была наша недоделка, не
ваша. Закрыто 20 сентября (`Z-45`): показывайте причину как есть.** Ниже — как
было, чтобы понять, почему в интерфейсе могли остаться осторожные формулировки.

Формально `rounds` значит «кончились раунды ремонта», то есть «дай больше —
починю». Замер 19 сентября показал, что это неправда: прогон с восемью раундами
вместо трёх встаёт **на четвёртом** с причиной `floor` и **с тем же числом
дефектов**. Числа в отчёте были верные, врала только строка «чем встала».

Теперь после цикла у ремонта спрашивают, изменил бы он план ещё раз: не изменил
бы — значит пересборка дала бы тот же файл, и причина `floor`. `rounds` остаётся
только там, где добавка раундов правда помогает. **Так что `stopped` можно
выводить дословно**, а осторожное «ремонт остановлен» больше не нужно.

### Проверка вёрстки требует Windows с Office

`--verify` поднимает **настоящий PowerPoint**. На сервере без Windows и Office
стадия выключится сама — и интерфейс обязан сказать об этом словами, а не
показать ноль дефектов (см. правило выше).

### Публичный стенд без `--verify` и с паролем

Сервис открывает загруженные `.pptx` **настоящим PowerPoint**. Пускать на такую
машину произвольные файлы из интернета — реальная поверхность атаки, а не
теоретическая. Если стенд выставляется наружу: пароль обязателен, `--verify`
выключен.

Полноценный демонстрационный прогон с проверкой вёрстки снимается на видео с
домашней машины — это разрешено организаторами и в составе сдачи.

### Никакой подгонки под наш текст

В интерфейсе не должно быть примеров, подобранных так, чтобы движок выглядел
лучше. Проверять будут на **своём** шаблоне и **своём** тексте. Наши примеры
лежат в `examples/` и годятся как заготовки в поле ввода — но пользователь
обязан иметь возможность стереть их и вставить своё.

## 8. Как начать

```bash
git clone <ссылка на репозиторий>
```

```bash
git config user.name "Имя" && git config user.email "почта"
```

Настройки — свои: авторство коммитов должно быть настоящим.

```bash
git checkout -b web
```

Скачать корпус шаблонов — **раньше, чем запускать тесты.** В репозиторий они не
коммитятся, они чужие, а без них часть тестов пропускается — какие именно,
`AUDIT.md`, «Что покрыто хорошо, а что нет». Пропуск виден и назван причиной,
но прогон при этом зелёный.

```bash
python tools/fetch_samples.py samples
```

Проверить, что движок работает. С корпусом на месте законных пропусков два, и
оба не про корпус: в синтетической фикстуре нет раскладки со слотом-списком и
не остаётся пустых нетекстовых слотов — тесты честно говорят об этом вместо
того, чтобы проверять пустоту.

```bash
python -m pytest
```

Собрать первую презентацию руками, чтобы увидеть, с чем предстоит работать.
Серверы модели не подняты — сборка пойдёт путём без модели и скажет почему;
`--llm off` — сразу, не стучась к серверу.

```bash
python -m mimeo build samples/business_plan.pptx examples/content-mimeo.md -o out --output out/deck.pptx
```

Дальше — свой каталог, свои зависимости, работа в ветке `web`, слияние через
Pull Request.
